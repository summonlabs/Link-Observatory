# Link Observatory - Proof Surfaces

Every claim this release makes is labelled REAL, SYNTHETIC or UNSUPPORTED. The
labels are not commentary: REAL means a test or a build on this host produced the
result, SYNTHETIC means the input was generated by the runtime itself and is
labelled as such, and UNSUPPORTED means the capability is absent and is never
claimed anywhere in the code, the tests or the README.

### Commands behind the REAL results

Every row above comes from one of these commands, run from the repository root:

    # builds (all three: warning-free, warnings-as-errors on)
    cmake --preset release && cmake --build --preset release
    cmake --preset debug   && cmake --build --preset debug
    cmake --preset asan    && cmake --build --preset asan

    # suites
    build/release/tests/linkobs_tests.exe
    build/debug/tests/linkobs_tests.exe
    build/asan/tests/linkobs_tests.exe
    build/release/tests/linkobs_process_tests.exe
    build/debug/tests/linkobs_process_tests.exe
    build/asan/tests/linkobs_process_tests.exe

    # the ASan binaries need the MSVC ASan runtime directory on PATH (row R4, U8)
    # ...\BuildTools\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64

    # benchmark
    build/release/benchmarks/linkobs_bench.exe

    # package and downstream consumer
    cmake --install build/release --prefix <prefix>
    cmake -S tests/downstream -B <dir> -G Ninja -DCMAKE_BUILD_TYPE=Release \
          -DCMAKE_PREFIX_PATH=<prefix>
    cmake --build <dir> && <dir>/downstream_consumer.exe

The transport and process rows are produced by the suites themselves: they bind a
real listener, connect a real socket, spawn real child processes and exchange real
frames. Nothing in those rows is simulated in-process.

### What is deliberately not measured

Absent from the REAL table, and therefore not claimed: cache behaviour, allocator
behaviour, worst-case latency, sustained throughput over hours, behaviour under
memory pressure, and behaviour when the host clock steps backwards or forwards
during a run. The last of those is handled by construction (freshness is
recomputed from the injected clock and a future-dated observation is never
treated as extra fresh) and is covered by `domain.a_future_timestamp_is_not_extra_fresh`,
but the runtime has never been driven by a stepping system clock on real
hardware.

## SYNTHETIC - generated input, labelled as generated

| # | Surface | Statement |
| --- | --- | --- |
| S1 | Benchmark input | The benchmark generates its own record set with its own generator. It is not a capture from any device. |
| S2 | Property and randomised test input | The property suite builds record streams from a seeded generator in `tests/support/fixtures`. Every generated source declaration carries `provenance=synthetic` and every generated record inherits it, so the runtime labels the evidence as synthetic through ingestion, classification, explanation and export. |
| S3 | Adversarial test input | Malformed records, forged digests, replayed revisions, retired generations, backwards clocks and oversized fields are constructed by the tests, not observed in the field. |
| S4 | Link names, endpoint names and capacities in tests | Invented for the tests. `capacity-in-bps=100000000000` is an example value, not a measurement of any real port. |

### The labelling path, end to end

Synthetic input is labelled at the source declaration, not at the point of
reporting, so the label survives every stage:

1. the generator in `tests/support/fixtures` emits a source declaration with
   `provenance=synthetic`, and every observation record it produces is
   attributed to that source,
2. `parse_record` requires the provenance field, so a generated stream cannot
   be replayed without it,
3. `LinkRegistry::register_source` refuses a source that declares `unknown`,
   so there is no "unlabelled" default to fall into,
4. `EvidenceStore::accept` copies the provenance class into each stored
   evidence record at acceptance time,
5. the classifier reports the winning record's class in every family report, and
   `explain` prints it on the metric line,
6. `export` writes the record back out with the class intact.

The runtime never re-labels synthetic evidence as real. `ProvenanceClass` is
captured at acceptance time, is carried on every stored evidence record, is
reported in every family report and explanation, and cannot be promoted by a
payload field because authority and provenance come from the locally registered
source record, not from the observation.

### Why the benchmarks are synthetic by construction

A benchmark that drove a real switch would be measuring the switch. The benchmark
generates its own links, sources and counter streams so that the number it prints
is a property of this runtime on this host and nothing else. The generated
records carry `provenance=synthetic`, so a snapshot produced by a benchmark run
can never be mistaken for a capture of real infrastructure: the label is in the
evidence, not only in the file name.

## UNSUPPORTED - absent, and never claimed

| # | Not supported | Why it is not claimed |
| --- | --- | --- |
| U1 | Real switch, ASIC, PHY or serdes interaction | The runtime has no device access path. There is no register model, no lane model and no programming interface. Every statement about hardware would be fabricated. |
| U2 | RDMA, InfiniBand, NVLink or any specific interconnect semantics | No protocol-specific counter, lane, symbol or credit concept is modelled. Error classes are vendor-neutral and are supplied by the caller. |
| U3 | Vendor telemetry protocols and collectors | There is no SNMP, gNMI, REST, streaming-telemetry or vendor SDK integration. Telemetry reaches the runtime as LOR text from a source the operator runs. |
| U4 | Multi-host or multi-switch fabric behaviour | The only real transport proof is a loopback TCP socket on one host between two processes. Nothing about multi-host fabric convergence, partition behaviour or cross-switch correlance is claimed or tested. |
| U5 | Snapshot authentication | The snapshot is integrity checked with SHA-256, which detects accidental corruption and truncation. It is not signed and there is no key material, so it does not authenticate the writer and is not tamper-resistant against an attacker who can rewrite both the payload and its digest. |
| U6 | AddressSanitizer leak detection on this platform | The MSVC AddressSanitizer on Windows does not provide LeakSanitizer. Memory-error detection was exercised (R4); leak detection was not, and no equivalent coverage is claimed for it. |
| U7 | Compilers and platforms other than MSVC on Windows x64 | GCC and Clang warning configurations exist in the build, but no GCC or Clang compiler was available on this host, so no non-MSVC build or run is claimed. The transport code contains POSIX socket paths that were never compiled here. |
| U8 | AddressSanitizer runtime deployment | The x64 ASan build links against the MSVC ASan runtime, but the build does not copy `clang_rt.asan_dbg_dynamic-x86_64.dll` next to the test executables. Running those binaries without the MSVC ASan runtime directory on `PATH` fails with `STATUS_DLL_NOT_FOUND` (0xC0000135); the R4 result was obtained with that directory on `PATH`. |
| U9 | Timing or throughput guarantees | No latency, jitter or throughput guarantee is made. The benchmark reports what one host measured once; it is not a performance contract. |
| U10 | Automatic failure detection | The runtime reports what its evidence supports. It does not and cannot decide that a link has failed when no source reports anything about it; absence of evidence yields Unknown, Stale or Unsupported. |

## How the labels are enforced

The distinction is not documentation-only:

* `ProvenanceClass` is a required field of every source registration, and a
  source that declares `unknown` is fenced at ingest with
  `FenceReason::UnsupportedProvenance`. There is no default.
* The evidence store copies the provenance class into each stored evidence
  record, and the classifier reports the winning record's class in every family
  report and explanation line.
* `SupportState::Unsupported` is a first-class outcome. A metric family that no
  configured source supplies is reported as unsupported, and the link state
  becomes Unknown through rule R-810 rather than being reported as healthy.
* The command line tool never prints a wall-clock time, a host path or an address
  in a report, so a report cannot accidentally imply an observation that the
  runtime did not make.
